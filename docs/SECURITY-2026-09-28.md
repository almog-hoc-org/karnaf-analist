# 28.9.2026 — user data in public backups

## What happened

The repository `almog-hoc-org/karnaf-analist` is public. From 2.8.2026 the weekly
backup (`deploy/karnaf-backup.timer` → `scripts/publish-backup.sh`) uploaded
`app.db.gz` to that repository's Releases, unencrypted. Nine releases, 2.8–27.9.

`app.db` holds, for every account: email, name, phone, scrypt password hash,
Google subject id, mailing consent, credits, saved deals, followed cities,
feedback text, and the `sessions` table. Session tokens were stored raw and
lived 30 days, so a downloaded backup was enough to sign in as any user with a
live session.

## What the code does now

| Change | File |
|---|---|
| `app.db` is uploaded only encrypted with `age` (`app.db.gz.age`); no key → not uploaded at all | `scripts/publish-backup.sh` |
| Release pruning reads tags as JSON; it had never deleted anything | `scripts/publish-backup.sh` |
| Restore reads the encrypted asset, finds the newest tag, writes to `KARNAF_DATA_DIR`, stops the container while swapping | `scripts/restore-db.sh` |
| Sessions stored as `h1:` + SHA-256 of the cookie token; raw legacy rows deleted on first use after deploy (everyone signs in again once) | `lib/sessionToken.ts`, `lib/auth.ts` |
| Google sign-in linking to an existing password account makes the password unusable and ends its sessions (the mailbox owner wins); it no longer switches mailing consent back on | `lib/auth.ts` |
| Admin table browser no longer shows `client_deals`, `tracked_cities`, `credits_ledger` | `app/api/admin/tables/route.ts` |
| The public login card no longer links to `/admin` | `app/login/page.tsx` |

## Operator steps

1. **GitHub:** Settings → General → Danger zone → Change visibility → **Private**.
2. **Optional, stricter:** delete the `app.db.gz` asset from each of the nine
   `data-*` releases (the deal archive can stay). Deleting is irreversible.
3. **On your own computer** (not the server): `age-keygen -o karnaf-backup.key`.
   Keep the file somewhere safe (password manager). It prints a public line
   starting `age1…`.
4. **On the server:** `apt install age`, then add to `/etc/karnaf/backup.env`:
   `KARNAF_BACKUP_AGE_RECIPIENT=age1…`. Check with
   `bash scripts/publish-backup.sh --dry-run` — it must list `app.db.gz.age`.
5. **Restore later:** `KARNAF_BACKUP_AGE_IDENTITY=/path/karnaf-backup.key KARNAF_DATA_DIR=/var/lib/karnaf/data bash scripts/restore-db.sh`.
6. **Legal:** this is personal data that was publicly reachable. Ask a lawyer
   whether it must be reported to the Privacy Protection Authority and whether
   users should be told.
